# 单细分消费者洞察与产品开发

只接收用户已选择的一个细分市场及明确交接的完整商品/关键词清单。不重算Top3、不扫描猜测项目、不修改上游、源数据库或历史报告。目标是证据支持的产品概念与验证计划，不冒充实物打样和真实用户测试。

## 受保护鉴权与配置

- 根目录 `config.json` 仍是唯一后端配置，字段 `backend_url/backend_token` 与0600校验不变。这是本地格式检查，不是服务端在线验证。
- Flyfus与ScrapeCreators独立API配置沿用各自 `.env`，不迁移后端、不合并文件、不改读取优先级、Key、端点、请求头、权限、脱敏、浏览器登录态或收费不确定请求的恢复逻辑。
- 不回显凭据、不把后端Token用作第三方Key；不设置本任务points/credits上限，但每次请求实际或不确定消费分账。未配置的协作能力记录缺口，不自动注册、购买或提取新Cookie。

## 固定业务链

1. 读取 [输入契约](references/input_contract.md)，用 `scripts/single_segment_contract.py` 冻结单细分、统计期、前50评论候选、前5问答ASIN、前10问答关键词与完整竞品池。
2. 基于**完整关键词**归纳主体、限制、用途、场景，产出三个自然且互补的检索表达及支撑词；不是机械取前三词。采集前读取 [社媒与协作采集](references/consumer_voice_collection.md)，自动调度 `agent-reach` 与 `last30days` 配合现有ScrapeCreators获取社媒和网页原文。三层发现为裸表达、意图扩展、证据驱动查漏；意图词不作纳入门槛。
3. 读取 [Flyfus规则](references/flyfus_v5.md)。Amazon先前5ASIN，每ASIN最多1,000原始唯一评论；只有具体证据缺口才依序扩展，最多前50。社媒先200试采。4,000评论、2,000社媒、6,000总有效VOC均为参考目标，达到可暂停常规扩量，不强制达到且无需豁免；网页消费者声音计社媒，Alexa单列。
4. 读取 [数据契约](references/consumer_voice_contract.md) 和 [运行工作流](references/consumer_voice_workflow.md)，使用 `scripts/consumer_voice_local_reprocess.py` 做 Python 全量标准化、身份合并、声明式规则、多标签、稳定need_id与精确统计；未命中/冲突/隐含/新颖表达进入小批模型复核。不得把规则结果伪装成Agent复核。
5. 不做语义去重；不同原始记录即使同人同观点仍分别计声音，作者单独计数。同一原记录重复抓取只保留来源关系。真实购买询问、外观、替代用途分层纳入；研究资料与模型摘要不冒充消费者发言。全历史、六类语义任一命中（OR）、不输出置信度分数。
6. Codex自动逐批复核、验收回填和重算至未执行为0；已审但证据不足保留理由且不计有效。规则结果固定种子分层抽检5%，评论和社媒各至少50条（不足全检），重点异常另查。首采、十类查漏、已采数据处理、质量及三个方向通过即可停止。数量不足本身不触发补采，20/5/2与三批饱和不作硬门槛。
7. Python以稳定need_id生成全量证据包。对每个`eligible=true`需求，先用`consumer_all_history_report.py prepare-need-summaries`导出带证据指纹的消费者语义包；Codex按需阅读证据后输出“消费者声音语义总结、对应需求描述、引用证据ID、复核版本”，再用`import-need-summaries`严格导入。报告固定展示这两项和简短证据使用边界；替代解释、逐条原声和长例外只留审计文件。随后Codex自动按需求综合判断KANO，仅提及率>=3%入队；其余below_threshold不分析展示。机会采用双轨：具体新需求/DIY绕行严格按具体need_id全量计数，>=0.5%才展示；既有需求改进机会同样需>=0.5%，但明确不等于市场空白。不得借宽泛需求频次为具体机构过门槛。Alexa全部已保存答案用于选购维度、商品声明核验与测试约束；每条有终态、来源关联和关键未知处置。
8. 读取 [产品开发契约](references/consumer_product_development.md)，新运行实际执行 `consumer-12-role-workshop-3.1` 的十二个独立角色七阶段工作坊。先用全量逐条机会语义复核把原声拆为“表达→结果→候选机制”；六个发散角色各提出三种不同机制，至少18个原始创意，整合6–9个候选，再经九位评审者逐案核对用户收益、机制差异、普通替代方案与配件组合、代价和验证。KANO只决定需求的设计策略，不机械映射MoSCoW。恰好三个通过创新评审的正式打样验证方向；每案分别定义研究打样版与暂定上市V1。每案从销量前10%商品中按已确认核心特征重叠、销量、ASIN选一个主对标；未知不作缺失。必须呈现竞品已有设计→需求依据→我方升级→预期改善→取舍→测试。
9. 概念图使用 Image Gen。每个冻结方向生成产品整体、关键结构/升级机制、使用场景三张图；同案后两图参考首图，所有图嵌入新运行目录的单文件离线HTML。图像只能转译工作坊冻结定义，标注概念示意，不能补造功能或冒充工程验证。
10. 读取 [固定报告母版契约](references/consumer_report_layout_contract.md)，新报告固定使用 `scripts/consumer_all_history_report.py` 与 HTML 1.5.0 共享模板，直接生成用户已确认的排版，不再逐次补丁修改HTML。前部依序展示清洗漏斗、Amazon/站外抓取量与清洗后数量、总有效VOC与采集覆盖、核心结论和证据详情。产品方向先任务与成本、后整体图与开发详情；功能证据、KANO决策链、双版本MoSCoW和六步设计过程均桌面每行两项、窄屏单列。每个方向后紧接其精简竞品对标，末尾统一展示运营/开发行动和推进/停止条件，不显示角色名单、空阶段卡或内部执行术语。渲染前用 `prepare-report-copy` 准备摘要包，Codex从冻结产品与竞品资料整理短文，再用 `import-report-copy` 导入新的展示分析文件；来源变化须重做摘要。数字、状态和竞品指标动态读取，未知不作完成，销量与销售额只读子体列。深色页头、侧导航、十章及主要依据需求卡保持固定；完整证据和评审过程留审计文件。完整交付执行 `render --final`，并做离线、响应式与打印检查；渲染不代表样机或用户测试完成。

## 上下文与交付

疑难请求最多20条，输入目标8,000 tokens并预留系统/输出预算；长记录完整分段、父ID合并，不截断或增计声音。保存批次、输入哈希、规则/复核版本、已验收输出；缺ID/重复ID/虚构引文拒绝入库。按需求读取统计与原声索引，不将全部VOC塞入一段摘要。

历史schema仅兼容读取；新运行使用新目录。源码规则、schema与参考文档须同步；v2.3 全量机会复核由 `scripts/consumer_opportunity_recheck.py` 准备/验收，逐条结果绑定原文、上下文与既有需求快照；派生分析仍由 `scripts/consumer_voice_v22_enrich.py` 生成新版本快照，并建立统一需求登记，报告仍由 `scripts/consumer_all_history_report.py` 输出。无日期筛选；若交接看板，用 `--dashboard` 保护哈希，没有看板不阻碍单细分。

本Skill更新本身不触发正式采集、工作坊或报告重跑。采集任务中协作Skill缺失/受阻时说明实际状态，不把“已计划”说成“已调用”。
