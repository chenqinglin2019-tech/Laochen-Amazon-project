# 十二角色产品开发工作坊与完整商品池核验

## 启动与运行时登记

在全历史规则处理、疑难复核、质量验收、全量机会语义复核和需求统计后，创建新的工作坊目录。新运行 Analysis 必须包含 `business_rules_version: voc-prd-v2.3`。总有效6,000、Amazon4,000、社媒含网页2,000均为参考目标，数量不足不阻止工作坊或正式方向；无证据和未知适用性仍不能当正式需求。达到数量可暂停常规扩量进入分析，业务完成停止要求处理、质量、十类线索查漏和三个通过评审的方向完成。

```bash
python3 scripts/consumer_product_development.py prepare \
  --coding <CODING> --analysis <ANALYSIS> --output-dir <WORKSHOP> \
  [--insight-dir <RUN_DIR>]
```

新目录采用 `consumer-12-role-workshop-3.1`。它生成十二份任务书、冻结证据包和阶段清单。主智能体使用既有建群／子智能体创建能力按可用并发分批安排任务；本脚本不创建群组、不创建智能体、不读取 Token 或 API Key。

每个阶段产物完成后，主智能体根据既有运行时返回的实际 agent ID 和执行回执整理输入，再登记：

```bash
python3 scripts/consumer_product_development.py register-roles \
  --workshop-dir <WORKSHOP> --input <ROLE_RUNTIME_RECEIPTS.json>
python3 scripts/consumer_product_development.py validate-stage \
  --workshop-dir <WORKSHOP> --phase <PHASE>
```

登记输入为 `consumer-workshop-role-registry-input-3.0`，每条 `executions[]` 必须包含 `role`、`phase`、`agent_id`、`runtime_receipt_ref` 和固定的 `artifact` 文件名。脚本核对角色任务哈希、产物中的 agent ID 与登记回执，并禁止一个 agent ID 担任两个角色。更换同一角色实例时必须提供前一 agent ID 与替换原因。登记是主智能体保存的运行时证据，不能仅凭角色产物自报身份。

## 十二角色和阶段

| 阶段 | 参与角色 | 必须留下的记录 |
| --- | --- | --- |
| 共情与定义 | 主持人、用户洞察、人因、市场策略、独立挑战者 | 任务书、需求证据表、使用流程、市场假设、反例与 HMW 问题 |
| 独立发散 | 人因、概念架构、工业设计、结构材料、跨界探索、市场策略 | 每人恰好 3 个互不可见且机制路径不同的创意；至少18个，包含用户矛盾、结果、动作改变、普通替代、机制、证据、假设和取舍 |
| 整合候选 | 概念架构师 | 6–9 个完整候选、来源创意、全部原始创意处置、每个关键结果至少两条机制路径、需求→KANO→机制决策链、功能边界和明确不做项 |
| 独立评审 | 用户洞察、人因、工业设计、结构材料、市场策略、制造成本、质量安全合规、原型验证、独立挑战者 | 每人审查全部候选；不适用也要说明原因；每项异议有唯一 ID；逐案记录用户收益、机制差异、普通替代方案与配件组合、代价、验证和创新评审结论 |
| 处置与修订 | 主持人、概念架构师、原型验证师 | 争议台账、候选修订、原型与测试计划；未实测只能标记 planned/not_executed |
| 原评审者复核 | 九位评审者 | 对自己提出的每项异议确认接受处理或保留反对意见 |
| 收敛选择 | 主持人、概念架构师、独立挑战者 | 选择候选、选择依据、最终挑战立场；被标记为 block 的候选不能进入终稿 |

主持人管理阶段、保护独立发散、登记争议和决策依据；不替代任何专家角色，也不把九份独立评审写成虚构的对话。工作坊可根据未解决问题返回前一阶段；已变化的候选、后续评审和选择必须重做，旧完成回执不能复用。

角色任务始终区分消费者原声、证据推导和设计假设。评论、社媒和 Alexa/Rufus 保持各自统计口径；Alexa 只可作为选购维度、承诺或待验证线索。现有完整商品池与研究信号通过冻结路径只读定位。影响分类或开发方向的关键缺口交主智能体定向补查；不能仅因未达数量目标扩量。补查改变证据快照后重新准备工作坊并重做受影响的判断和阶段，不复用失效回执。

## 最终方案与竞品核验

PRD v2.2 完整交付必须恰好三个正式方向，探索池单列；0、1、2或4个均不通过完整交付。不足三个时返回构思、整合和评审，阻断候选须修订或替换，不以颜色、名称或轻微配置凑数。每个方案必须提供目标用户／完整任务流／JTBD矛盾、功能与技术方案、结构／材料／外观、每项功能的消费者原声／推导／假设、KANO设计策略、候选机制的采用或拒绝理由、反证与风险、BOM 假设、原型目标、测试对象／方法／失败条件。未测试优势一律为预期。上述产品定义必须由十二角色工作坊冻结，后续不得由图像生成器补写。

评论默认采样前五 ASIN；完成当前批次编码后证据不足时，可按销量顺序扩展到前五十 ASIN。直接竞品核验使用上游推送的全部细分商品。对每个冻结的核心需求与设计亮点，逐 ASIN 记录 `covered`、`not_covered` 或 `unknown`；能力未知时不能宣称唯一性。

```bash
python3 scripts/consumer_product_development.py finalize \
  --workshop-dir <WORKSHOP> --decisions <WORKSHOP>/decisions.json \
  --competition-audit <RUN_DIR>/competition_audit.json \
  --output <RUN_DIR>/social_voice_development_analysis.json
```

`finalize` 重新校验冻结证据、十二角色登记、所有阶段产物、争议闭环、终稿候选来源和完整商品池核验。它把方案内容哈希写入工作坊完成回执；终稿方案被改写后，报告生成会拒绝使用旧回执。

每个方向先从完整商品池销量前10%（向上取整，销量并列一并纳入）中筛候选；再按已确认核心特征重叠数降序、销量降序、ASIN升序选择主对标。新增升级机制不能反向变成竞品必须已有的筛选条件；`unknown`不能写成没有。固定说明：竞品已有设计、用户问题与需求数/占比、我方升级机制、预期改善、成本/体验取舍、验证方法。唯一性结论限定为“在本次核验的细分商品池快照中未发现直接对应商品”。

在工作坊冻结并完成竞品复评后，才可调用 Image Gen。每个方向按同一冻结定义输出三张：整体外观、关键结构与升级机制、使用场景/状态。提示词明确引用JTBD、功能与技术方案、结构、材料与外观；结构图和场景图必须使用整体外观图作参考以保持一致。图片是概念示意，保存路径、SHA-256和方案版本写入资产清单；不当作工程、合规或性能证据。

## MoSCoW、设计思维与历史兼容

每个 v2.2 正式方向有两套不互相替代的范围表：`research_prototype` 用于本轮打样必须回答的问题，`provisional_v1` 用于验证通过后才可能承诺的上市版本。每项记录优先级、对应需求/实现、未做后果、替代、依赖、成本假设和验收。研究版 Must 可以是上市版 Won't；KANO M/O/A/I/R 不得直接映射 MoSCoW。Must 的依赖必须在同一版本范围内闭合。

设计思维阶段统一为同理、定义、构思、原型、用户测试、迭代；每一阶段记录状态、产出、依据与下一步验证。视觉概念完成不等于实物原型完成，测试计划不等于用户测试完成。九名评审者的创新评审只能确认“概念可进入打样验证”，不能替代性能、合规或用户测试结论。

每个最终方向必须将上述六步写为可渲染的 `design_thinking_process` 对象，六项顺序和字段固定：`label`、`status`、`output`、`basis`、`next_validation`、`decision_gate`。其中“同理、定义、构思”的依据至少关联冻结需求/KANO/机会或竞品快照；“原型”明确视觉或实体状态；“用户测试”和“迭代”不得把计划写成已执行。报告将该对象固定渲染为产品卡片风险/报告状态之后的可展开六步过程；没有对象或字段不完整时，报告只可输出阶段性提示，不能称为完整产品开发交付。

## 历史兼容与边界

历史五角色工作坊目录继续按 v1 读取和 finalize；`voc-prd-v2`/`voc-prd-v2.1` 使用 `consumer-12-role-workshop-2.0` 原契约；`voc-prd-v2.2` 使用 `consumer-12-role-workshop-3.0`，新 `voc-prd-v2.3` 使用 `consumer-12-role-workshop-3.1`。旧产物不自动补填 v2.3 的机会复核、KANO决策链、创新评审或双MoSCoW字段，也不改变历史报告结论。十二角色工作坊不允许 `role_simulation` 降级。

本模块不改变上游 Skill、建群逻辑、鉴权、API Key 写入和读取、供应商端点、额度账本、浏览器登录态或采集逻辑。

## 面向运营与开发的报告摘要

工作坊及完整商品池核验完成后，按 `consumer_report_layout_contract.md` 准备并导入 `consumer-report-presentation-1.0`。主智能体依据每案已冻结的定义与竞品资料，给出研究状态、运营先确认事项、开发先完成事项、推进/停止条件，以及六项简短对标结论和适用边界。摘要不改变方案、创新评审、成本或验证结果；绑定当前产品与竞品指纹，保存在顶层 `report_presentation`，禁止往已签版产品对象补字段造成工作坊哈希失效。

HTML固定展示每案对标指标及短卡，紧跟对应产品方向；不重复长表或完整审计段落。十二角色的名字、阶段回执和异议闭环保留在审计文件，报告展示其对运营与开发的行动含义。旧分析缺少摘要时仍可阶段性渲染同一布局，但明确标为待补；新的完整报告必须先补全摘要。

## PRD新版分析与核验字段

先导入按需求综合判断的KANO及Alexa正文分析，方法见consumer_voice_workflow.md。不同状态须实际处理，不得把pending当信息不足已审结。工作坊只输出概念和验证计划；斯坦福五模式是共情、定义、构思、原型、测试，十二角色为本Skill自定义组织，不冒称真实用户实验。

新版competition_audit的core_requirements使用requirement_mapping关联最终features与need_ids；product_coverage每项需求都有requirement_evidence.rationale，covered/not_covered还须source_refs，未知明确unknown。主对标与sales_benchmark均来自冻结完整池，sales/sales_period对应冻结值；销量标杆为最高销量（允许并列）。无资料不能声明市场不存在。

每方向功能证据区分consumer_explicit/evidence_inference/design_hypothesis；核心需求必须有当前细分适用的真实支持原声，允许非核心工程假设并明确验证方法。BOM标币种、范围和假设，未获供应商报价不称报价；原型计划明确用户任务、度量、通过/失败标准和迭代，不伪造测试结果。零方向只能是待继续工作状态，不能通过PRD v2完整报告验收。
