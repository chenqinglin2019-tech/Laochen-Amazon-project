# 消费者洞察与产品开发报告固定母版契约 2.5（HTML 1.5.0）

本契约固化2026-10-04用户确认的最后一份HTML排版，包括MoSCoW两列修订。新运行直接由共享生成器产生，不能依赖事后HTML补丁。母版固定布局与阅读层级，具体产品、数量、价格、状态和摘要全部从当前运行读取；历史报告只读兼容。采集、鉴权、数据库、业务规则和工作坊验收不变。

## 页面骨架与前部

- 保留深色简洁页头、白色卡片、浅灰底、侧导航、蓝色信息强调和橙色产品开发强调，使用本地系统字体、原生details与锚点，无远程脚本或样式。
- 十章节及导航顺序固定：核心结论、全量清洗、六类消费者表达、Alexa洞察与验证、需求与口碑、细分市场声音、KANO、双轨产品机会、三个产品开发方向、方法与限制。全量清洗保留唯一`#funnel`锚点，正文位置移到核心结论前部，不在后面重复。
- 前部固定顺序：页头 → 清洗漏斗 → 四张分渠道数量卡 → 总有效VOC与候选子体覆盖 → 核心结论及主要需求提及率 → Amazon证据分层与处理状态 → 默认折叠口径详情 → 核心需求依据、反证与适用性。
- 四张数量卡依序为Amazon评论抓取量、Amazon清洗后有效评论、站外VOC抓取量、站外清洗后有效VOC；默认桌面四列，较窄屏两列，手机单列。有效VOC总数和采集覆盖单独组成摘要栏。保留原有基线增量及接口失败说明。
- 抓取量使用`funnel.platforms[].hard_unique_records`，有效数使用`qualified_consumer_voices`，站外汇总所有非Amazon平台（含被排除的原始网页或其他站外记录）；有效集合仅统计清洗后保留项。重复抓取同一原生记录只算一次。明确排除、待复核、已审信息不足互不替代。
- 总量不一致、重复平台、缺字段或未核对数据标为未提供；不推算原始数量、不把接口失败当零评论。旧字典平台数据只可提供有效数。数量/比例均动态读取，禁止写死本次样例数字。
- `report_front`保留采集标签、基线、候选覆盖和Amazon适用性分层。覆盖须成功+失败=候选；三项分层之和须等于Amazon有效数；不满足时显示未提供，不作通过。
- 前部CSS使用`.voc-front`等局部范围；“核心需求依据、反证与适用性”以下的需求卡和其他章节不被全局覆盖。

## 主要依据需求卡

仅渲染`eligible=true`，按冻结统计顺序；等宽两列、窄屏单列。每张需求卡依序展示：

1. 需求名称、作者数、讨论数、渠道数、声音数及全量VOC占比。
2. 消费者声音语义总结：场景、障碍、期望与后果。
3. 对应需求的具体描述：可设计、可验证的边界。
4. 简短证据使用边界：当前/历史/未知结构计数，完整原声与例外在审计文件。

总结仍使用`consumer-need-semantic-summaries-1.0`导入，覆盖全部主要依据并绑定证据指纹；指纹变化需重新归纳。原声正文、代表留言、ID列表、逐条替代解释、十类线索执行表和独立验证路线不进报告正文。

## 产品方向的固定阅读顺序

完整交付恰好三个正式方向，阶段性报告保留当前数量和空态。方向区主标题固定两行：第一行“产品机会与开发”，第二行“正式推荐产品方向”及不可拆开的数量标签。方向导航链接与卡片ID一一对应。

每个方向从上到下固定为：

1. 编号、所属细分、产品名称、阶段标签。
2. JTBD任务卡、目标消费者与使用场景、目标价格/BOM状态及报价边界。
3. 产品整体概念图独占一行；关键结构和使用场景两图在原生展开区，保留概念示意、离线内嵌、懒加载及图片版本校验。
4. 核心功能与技术方案；风险、依赖及已定义的放行条件。
5. 开发详情：结构/材料/外观、BOM前提、功能与消费者证据关系、KANO设计决策链、MoSCoW、量化验收、六步设计思维过程。
6. 本方向的竞品对标卡。它必须位于此方向结束处、下个方向之前，不能统一堆在最后。

功能证据、KANO决策链、**每个MoSCoW版本内部的范围项**、六步设计思维卡，桌面统一每行两项，间距20px、卡片顶端对齐；视口≤760px单列。研究/打样版与暂定上市V1仍上下分组，组内分别两列，不能把两个版本误作两个项目。量化验收保留独立字段卡，技术细节完整保留；不再在方向内展示横向宽表。

六步依序同理用户、定义问题、提出创意、制作原型、用户测试、迭代优化，各有状态、产出、依据、下一步验证及决策门槛。机器状态转成业务状态；视觉概念、实体打样、测试计划和实际测试独立标记。风险及停止条件不能因缩短文案被删除。

## 精简对标和开发行动

- 每案对标显示简短商品名、真实商品链接/ASIN、历史价格、子体销量、子体销售额、样本内排名及统计期。只读冻结的子体销量与子体销售额，不读父体/月销量/月销售额；未知销售额不以价格×销量补算。
- 两列短卡固定六项：竞品已确认、本方向拟增加、希望改善什么、新增投入与取舍、首轮怎么验证、什么情况停止。底部显示适用边界；对标选择规则默认折叠。
- 主对标仍按冻结完整商品池前10%（并列保留）及已确认特征重叠/子体销量/ASIN选取；不同方向可以选中同一ASIN，不能为排版编造不同竞品。基础重叠不是升级有效或市场空白证明。信息服务的首饰参考与服务效果对照需明确区分。
- 三个方向后统一显示“开发评审结论与下一步”：每案简短状态 + 运营先确认 + 开发先完成 + 推进与停止条件。删除面向读者无用的角色名单、空阶段卡、agent/root/phase等运行术语。实际十二角色执行与异议原件仍留审计文件，不改变工作坊验收。

## 来源绑定的展示摘要

展示摘要使用顶层`report_presentation`，不修改已冻结的`product_concepts`、竞品核验或工作坊哈希。先准备空包，Codex读完整产品定义、竞品证据和反证后填写，再严格导入：

```bash
python3 scripts/consumer_all_history_report.py prepare-report-copy \
  --analysis <冻结开发分析.json> --output <待整理摘要.json>
python3 scripts/consumer_all_history_report.py import-report-copy \
  --analysis <冻结开发分析.json> --presentation <已整理摘要.json> \
  --output <新展示分析.json>
python3 scripts/consumer_all_history_report.py render \
  --analysis <新展示分析.json> --output <新报告.html> --final
```

摘要包为`consumer-report-presentation-1.0`，含`review_version`、`product_directions[]`。每案字段：

- `concept_id`与`source_sha256`：准备命令根据当前方案与对应competition_audit行产生，原样回填；方向改变或竞品证据改变时必须重新整理。
- `status/operations/development/decision`：研究状态、运营任务、开发任务、推进/停止条件；每项1–220字。
- `benchmark.existing/proposal/value/tradeoff/test/stop/boundary`：六项对标与适用边界，每项1–220字。以短句提炼当前证据，不硬截断长审计、不造已测试优势或商业结论。
- `mechanism_labels`：本案机器机制标识到简短业务名称的映射，不展示内部枚举。
- 可选`benchmark_name/benchmark_title`：1–80字，仅优化展示，不改变ASIN与商品属性。

导入检查完整覆盖、重复/未知方向、来源指纹、字段长度及运行术语。它不代替主智能体的语义审查。缺少摘要的历史分析可阶段性渲染同一格式并明确待补；新完整交付必须有已验收摘要，`--final`会拒绝缺失数据。禁止把此报告的产品、销量或消费者结论复制到其他细分。

## 渲染与验收

- 新报告只用`consumer_all_history_report.py`及共享`consumer_all_history_report.template.html`；版本1.5.0，旧版本仅兼容检查既有报告。禁止渲染后回退旧布局、注入原补采块或拼接重复对标表。
- 校验计数、来源绑定、章节/导航、三个方向/每案三图、六步过程、竞品与方向对应、四类展开区两列、移动单列、图片定义版本和离线CSP。
- 模板、生成器、schema、Skill入口与本契约同步更新。既有报告及原始分析保留；模板升级不触发重新采集、工作坊或收费调用。
- 桌面/手机展开状态、键盘操作、打印和离线为验证项；浏览器不可用时明确实际限制，不能声称视觉验收已通过。渲染成功不代表业务、样机或用户测试完成。
